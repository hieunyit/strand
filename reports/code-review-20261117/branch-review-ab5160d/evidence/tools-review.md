## Concrete findings

1. **[High] pg-strict writes DB credentials into world-readable artifacts.** `tools/diagnostics/pg-strict/main.go:248-279` interpolates `cfg.SourceDSN` and `cfg.TargetDSN` verbatim into `strand.yaml`, then writes the file with mode `0644` (`:278`). Trigger: invoke the supported `-source`/`-target` options with credential-bearing PostgreSQL DSNs and a shared output directory. Impact: other local users can read database passwords from the profiling artifact, and reports may then preserve them. Evidence: direct source inspection; the configured default Docker DSNs are harmless, but custom DSNs are explicitly supported. Recommend create config with restrictive mode (and consider redacting/removing it after the child exits).

2. **[Medium] Browser repro can stop a pre-existing user container.** `tools/diagnostics/browser-repro/run.sh:13,19-20` unconditionally stops Docker container `strand-chrome-fixture` before `docker run` and stops that same name again in EXIT cleanup. Trigger: a different process already owns a container under that common fixed name. Impact: the harness disrupts a container it did not create, contrary to the stated isolated/owned-resource cleanup claim. Evidence: shell commands use fixed name and no ownership/container-ID check. Unique per-run names plus cleanup of only the created ID would avoid this.

3. **[Medium] Crash test does not assert persisted state exists.** `tests/e2e/toast_completion_crash_test.go:117-129` scans the state directory and computes `foundState`, but only logs it; the test proceeds identically when it is false. Trigger: Strand crashes before creating any recognized JSON/checkpoint/spool entry, yet later resume catches up through other state or a clean restart. Impact: the stated checkpoint/plan preservation invariant is not actually gated, while `results/09-toast-crash-gate.md` says preservation was verified. Evidence: no assertion/use of `foundState` after the scan. The later `waitSynced` and parity checks establish eventual convergence, not existence of persisted plan/checkpoint at crash time.

4. **[Low] pg-strict phase labels have a data race.** `tools/diagnostics/pg-strict/main.go:381,387-415,437` shares `currentPhase` between the polling goroutine and main goroutine without synchronization. Trigger: poll tick races the warmup-to-steady assignment. Impact: `metrics_timeseries.jsonl` may contain a misclassified phase sample and running the diagnostic under `-race` reports a race. Benchmark aggregate TPS uses explicit counter boundaries and is not derived from these labels. Evidence: unsynchronized cross-goroutine read/write in source; not dynamically exercised in this review.

## Follow-up: additional PG-strict findings (static review)

5. **[High] `-auto-docker=false` custom DSNs point at mutable databases and setup truncates them.** The flag allows external source/target DSNs (`main.go:100-102`), then `setupDatabases` creates `bench.accounts` and unconditionally `TRUNCATE`s it on both DBs (`:608-625`), drops `strand_strict_diag_pub` on source (`:628`), and recreates it (`:629`). The raw TPS phase then updates target row id=1 for three seconds (`:582-599`). Trigger: explicitly run against a real or shared database with `-auto-docker=false -source ... -target ...`; it can delete every existing row in `bench.accounts`, replace the source publication, and mutate row 1. No opt-in destructive confirmation, schema isolation, or preflight guard exists. The default AutoDocker=true means external DSNs are ignored unless caller also disables AutoDocker; that is an additional CLI sharp edge, but does not make the explicitly supported external-DSN path safe.

6. **[High] AutoDocker deletes any existing containers under fixed names before creating its own.** `main.go:131-140` chooses `strand-strict-diag-src/dst`, then runs `docker rm -f` on those names before starting containers, and repeats that command at cleanup. Trigger: a pre-existing user container has either name. Impact: it is force-removed even though the harness did not create it, violating ownership isolation and potentially destroying useful state. Static evidence; no Docker command run in this follow-up.

7. **[Medium] Reported `avg_batch_size` is rows per applied source transaction, not transactions per commit batch; the report then treats the local benchmark as explaining the user's 280–300 TPS.** Harness `main.go:475-477` divides `steadyRows` by `steadyTxns`; the source metrics count applied rows and source transactions, not batch commits (`internal/pipeline/pipeline.go:1815-1818`). Yet field/log/summary call it average batch size (`main.go:63,89,490-504`). Stored baseline says `avg_batch_size: 1` while `results/03-pg-profile.md:133,170-173` separately says txntrace observed ~3.36 txns/batch in single-client and ~31.30 in another run, demonstrating these are different quantities. Separately, report 03 calls its explanation the “exact physics” / “Root Cause” (`:7,138-168`) and assigns 2.5–3.5 ms storage fsync latency to the reported 280–300 TPS, but its measured baseline is 2669.8 TPS on local WSL2 (`evidence/pg-strict/summary.json`, `reproduces_280_to_300=false`) and no user-host storage latency or 280–300 TPS run is shown. The conditional arithmetic may be a hypothesis, but artifacts do not establish it as the user's root cause. Impact: misleading batch telemetry and unjustified root-cause confidence.
